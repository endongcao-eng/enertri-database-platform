# V4.1 数据库迁移与回滚

## 1. 原则

从 V4.1 起，表、字段、索引和约束的正式修改必须通过 `backend/alembic/versions/` 中的 revision 完成。禁止恢复以应用启动时自动建表作为生产升级手段。

## 2. 升级

### Docker

Dockerfile 使用 `entrypoint.sh`：

```sh
python scripts/migrate.py upgrade head
exec "$@"
```

数据库迁移失败时后端不会启动。

### 本地/运维命令

```bash
cd backend
python scripts/migrate.py upgrade head
```

成功输出示例：

```json
{"ok": true, "action": "upgrade", "baseline_stamped": false, "requested_revision": "head", "current_revision": "v4_1_foundation"}
```

也可直接使用 Alembic：

```bash
alembic upgrade head
alembic current
alembic history
```

## 3. 旧 V4.0 数据库升级

`app/migration_bootstrap.py` 会检查：

1. 数据库存在 V4.0 业务表；
2. 尚无 `alembic_version`；
3. 符合基线结构。

满足条件时先 `stamp v4_0_baseline`，再执行 `upgrade head`。这避免对已有表重复执行基线建表。升级会把 `users.role='student'` 转换为 `learning_user`。

## 4. 回滚

回滚一个 revision：

```bash
python scripts/migrate.py downgrade -1
```

明确回到 V4.0 基线：

```bash
python scripts/migrate.py downgrade v4_0_baseline
```

再次升级：

```bash
python scripts/migrate.py upgrade head
```

V4.1 回滚会删除新增基础表并恢复 V4.0 角色约束。回滚前务必导出 V4.1 任务、文件元数据和审计数据，备份 PostgreSQL 与 `/app/media`；迁移回滚不会自动恢复已删除的物理文件。

## 5. 后续结构修改流程

```bash
# 1. 修改 SQLAlchemy model
# 2. 创建新 revision（名称示例）
alembic revision -m "add video analysis fields"
# 3. 编写 upgrade() 与 downgrade()
# 4. 在空库和旧版本副本上测试升级
# 5. 测试回滚与重新升级
# 6. 提交 model + revision + 测试，禁止只提交 model
```

生产发布建议采用：备份 → 维护窗口 → 迁移 → 健康检查 → 冒烟测试 → 开放流量。高风险迁移应拆分为“先兼容加字段、再回填、最后收紧约束”的多个版本。

## 6. 验证查询

```sql
SELECT version_num FROM alembic_version;
SELECT action, outcome, created_at
FROM audit_logs
WHERE action = 'database.migration.completed'
ORDER BY id DESC;
```

V4.1 期望 revision：`v4_1_foundation`。
